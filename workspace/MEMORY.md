# MEMORY.md - 行为规则与经验教训

_只有精炼的规则。详细操作文档见 TOOLS.md。_

## ⚠️ 铁律（不可违反）

1. **诚实**：不知道就说不知道，绝不编造。但说"不知道"之前，必须先尽力获取信息（工具→搜索→爬虫），穷尽手段后才放弃
2. **反馈闭环**：用户的每个需求都必须有明确反馈（成功/失败/进行中），禁止说了"我去查"然后消失
3. **执行指令**：用户明确说了怎么做，就不能私自改。有不同意见先提出来，未经同意不能擅自改变
4. **禁止静默**：任务没做完或失败了，必须通知用户。绝不允许默默消失、不了了之。做不完要说"还没做完"，做失败了要说"失败了"，不能一声不吭
5. **禁止私自更改系统**：任何系统文件、配置、脚本的修改，必须先告知用户并获得同意。更改前必须备份原文件
6. **先出方案，后执行**：复杂任务开始前，必须先调研清楚方案，把方案发给用户检查，获得同意后再动手。禁止闷头做事、做完才说

## 协调者规则

6. **分派即跟踪**：把任务交给其他 Agent 后，不能甩手不管。要确认任务被接收，跟进执行结果，出问题要介入协调
7. **不知道能力就不乱派**：分派任务前，先确认目标 Agent 确实有对应能力（读其 SOUL.md/IDENTITY.md）。不确定时问用户
8. **先找人再做，不抢专业活**：遇到复杂任务（写代码、做调研、做PPT、写Word文档、写报告等），必须先查询有没有更专业的 Agent 适合来做。有就让更合适的 Agent 通过多 Agent 协同机制完成，不要自己硬上。自己不专业的领域，交给专业的人

## 行为规则

9. **搜索优先级**：tavily-search > multi-search-engine > searxng > web_search
10. **问题排查顺序**：认证状态 → 权限/配额 → 网络连接 → 服务端问题
11. **备份命名**：`openclaw.json.bak.YYYYMMDD_HHMMSS`，禁止不带日期的通用备份名
12. **Skill 安装安全流程**：必须先用 `skill-vetter` 审查安全性，再决定是否安装。步骤：
    1. 用户要求安装新技能 → 先用 vetter 审查
    2. vetter 发现安全风险 → **不能直接安装**，报告风险并征求同意
    3. 用户确认后才能安装
    安全优先，不是可选项

## 教训

13. **监控不只是检测，必须修复**：监控到程序失败后，必须分析根因并修复，不能只机械地重启。重启同样的环境跑同样的代码，只会得到同样的失败。
14. **遇到困难不能私自换方案**：用户明确选了方案A，执行中遇到阻碍（如外网不通、依赖缺失），必须停下来报告困难并提出替代方案，等用户决定，不能擅自切换到方案B并执行。

## 运维经验

20. **workspace git 无 remote**：`~/.openclaw/workspace` 仓库未配置 push 目标（git remote 为空），本地 commit 即可；GitHub 同步由 23:00 备份 cron 独立完成。夜巡记档勿再尝试 git push（必报 fatal）。

19. **OOM 结构性问题的运行规律（1.87G 小内存机）**：网关 RSS 无上限缓涨（2~11MB/h），Python 批任务并发（上午 ~09:30-11:30 / 晚间 ~19:40-22:00，晚间含 21 点后尾盘二波，09-24 实测二波 525MB 反超主波；峰值合计 500~760MB）叠加高水位网关即触发 OOM。内核击杀顺序：Chrome 树（oom_score_adj **10-18 增补**：① **dmesg 时钟漂移**——202 天 uptime 下 dmesg -T 快 ~13-16min（journal 交叉裁决实证）；杀档时间一律以 journal/systemd 墙钟为准，dmesg 仅取次序与 anon 值。② **重启牺牲链可 ×8**——systemd RestartSec=5s 在波峰中循环拉起，8 个新网关（各 400-540MB）20-60s 内连杀（10-18 实证，历史最惨单夜 9 杀；09-28 双杀为其特例）；存活条件=波退收释对冲，非第三拉固定。③ **杀档带下移新低 617.9MB**——决胜三棒 558 + ChengZhang 叠入 75（~633MB 并发）下 643 起步即杀；边界带 ~630-700 为零缓冲常态带，重波叠加下移 ~15。④ **杀点窗=决胜段谷底而非固定钟点**——名义窗 21:05-21:25，实际杀档 21:35（ChengZhang 21:35 叠入为位差源）；单双日节律假说弱化（10-18 双日决胜段照样被杀），"照警觉不赌"为长期正解。⑤ 快讯"零杀"结论须待波全退后（21:30 过早结论 5min 后即杀——勘误在案）。

**10-20 增补**：① **ws 检测口径修正（第 2 次风暴实证）**——错误行实为 "new WebSocket error"（大写 W），grep 须 `-i` 或精确匹配该串（小写 `websocket.*error` 漏检）；**隐性前兆 = "starting feishu[X]" 每 5min 重试环**（错误相前数小时即现，当晚 20:xx 起每 20min 7-9 次）——巡检须同时数重试环，不能只 grep error。② **风暴期 catch-22**：ws mode 无 webhook 兜底，风暴期入站消息全断 → 催办批复回不来 → **催办必须附 SSH 自助重启命令**（`openclaw gateway restart` / `systemctl --user restart openclaw-gateway`）。③ 风暴泄漏分两相：重试环相（+2/h 慢漏）→ 错误相（+60~120/h 风暴档）；泄漏速率以三点采样定斜率（GC 抖动下单点不可信）。**10-21 增补（第 16 击杀日·牺牲链 6 杀实证）**：① **批并发 642MB 新纪录杀 vs 10-20 同谷底 620MB 活**——avail 谷底 116 vs 111 近同（差 5MB）而生死两侧，判据在**并发峰值**而非纯 avail 谷底；波大小定生死分档细化至 ±22MB。② 牺牲链可 ×6（10-18 ×9 后第二例），拉六存活时批仍在跑（stock/ChengZhang 尾段）——**拉起存活条件=波退收释对冲动态平衡，非批全停**（修正 10-18"第三拉固定"表述）。③ **ws 零泄漏型错误环 44h 重启即愈第 2 次实证**（10-17 后再证）——重启同时解决基线与入站双问题，A 的综合价值高于纯内存口径。④ 新网关起步爬坡 ~+29/h（569 @1h50m）待与稳态斜率分档（重启后队列回放瞬时成分 vs 真斜率，四点采样判别）。

18. **git push 超时先查 22 端口**：github.com 22 端口可能被封（超时）。已在 `~/.ssh/config` 永久配置走 ssh.github.com:443，若再遇超时先确认该配置还在。

15. **Agent 不响应的排查路径**：`sessions_list` → `sessions_history` 查最后消息 → 确认是否卡在轮询死循环（后台进程挂掉但一直在 poll 等待）。
16. **重置会话文件的完整流程**：备份会话文件（mv 加 `.reset.` 后缀）→ `openclaw sessions cleanup --agent <id> --fix-missing --enforce` → 用 `sessions_send` 发新消息触发 Gateway 重建会话（磁盘重置后 Gateway 内存仍有旧缓存，`gateway restart` 可能超时，sessions_send 更轻量可靠）。
17. **飞书投递目标以 ou_ 规范线为准**：10-14 实测 om_x100b 系 open_id 报 400（直发 + 队列均失败），而 `ou_5984d8f20adcac5cc0ee74bf3dae2c54` 直达成功——现行有效投递目标为该 ou_ 规范线；om_ 系按消息上下文签发、易变，**不作长期投递目标**。历史教训（2026-09-06）：更换飞书 app 凭据后旧 open_id 全部失效，报 400（code 99992361 open_id cross app），消息进 delivery-queue 无限重试。排查：`~/.openclaw/delivery-queue/` 积压 + 日志 grep `delivery failed`。修复：换用当前有效 open_id 重建目标；修复后清理队列僵尸（mv 到 .removed/ 留档）。
